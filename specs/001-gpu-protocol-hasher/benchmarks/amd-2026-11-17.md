# RX 7900 XTX: HIP correctness and tuning results

The existing Blake2b search runs correctly through Sarek HIP on the local RX
7900 XTX. Interleaving two independent nonces per thread improves the warmed
one-compression paths by about **2.1%** in a confirmation run. It regresses the
two-compression path, so the default remains one nonce stream and 256 threads
per block. These experiments are on branch `perf/amd-hip-local`; they do not
change the defaults of PR #2.

## Confirmation measurements

Five samples of at least three seconds per variant, with alternating order;
medians include every sample. Gnonces/s means 10^9 candidates per second.

| Path | Default: block 256, one stream | Experimental: block 64, two streams | Change |
|---|---:|---:|---:|
| A, final block 46 bytes | 4.394 Gnonces/s | 4.487 Gnonces/s | +2.12% |
| B-host, final block 15 bytes | 4.385 Gnonces/s | 4.475 Gnonces/s | +2.07% |

Raw data: [confirmation.csv](amd-2026-11-17/confirmation.csv). One B-host
baseline sample fell to 3.226 Gnonces/s; it is retained in the CSV and median.
In the initial three-repeat sweep at the same block size (256), B-kernel was
essentially unchanged (4.212 to 4.215 Gnonces/s), while C fell from 2.105 to
2.068 Gnonces/s, about **1.8% slower**. See
[interleave-sweep.csv](amd-2026-11-17/interleave-sweep.csv).

Changing only the block size produced small differences in the initial
[block sweep](amd-2026-11-17/block-sweep.csv): its best median improvements over
256 threads were about 0.1% for A, 0.7% for B-host and 1.0% for B-kernel; C's
best result was already at 256. These small differences do not establish a
generally better default.

The production `--bench 1 --device 0` command independently reported
4.377 Gnonces/s on HIP and 0.0482 Gnonces/s on Native (32 threads) for the A
dump. That is one short sample, not the repeated confirmation experiment; see
[cli-bench.log](amd-2026-11-17/cli-bench.log).

## What was tested

Source for the paired sweep and confirmation:
`197b25cfbb2580535d5ec5a3f61fa7eaf9c0a728`. The preliminary block-only sweep
predates the addition of paired kernels; its CSV has no stream-count column.
HIP is registered alongside
the existing backends and pinned to the same Sarek commit. CUDA remains preferred
where available; this machine selects HIP device 0, the RX 7900 XTX. HIP device
1 is the Ryzen integrated GPU and was excluded from timing.

The experimental generator interleaves the statements of two independent
Blake2b compression streams. A thread processes loop digits 00..49 alongside
50..99, covering the same 100 candidates as the original sequential loop.
This also halves the number of loop iterations, so the measured gain cannot
be attributed solely to instruction scheduling. No tensor/cooperative-matrix
operations are involved, and no machine-instruction or spill analysis was
performed.

- Baseline kernels matched the host reference for 10^6 candidates on each of
  the four paths, on both the RX 7900 XTX and integrated GPU.
- Every block size (64, 128, 256, 512) and stream count (1, 2) matched the host
  prefilter reference for 10^6 candidates on each path. Returned candidates
  were also checked against Digestif.
- Paired kernels matched Native and the host reference on all four paths.
  Four full chunks, **400 million candidates** total, produced the same hit
  sets as the original Native kernels: 122931, 122394, 122094 and 122184 hits
  for F=46,15,9,3 respectively.
- The full unit/layout/CLI suite passed, including paired hit-buffer overflow
  subdivision. Two matches printed by the production HIP search were confirmed
  independently with `mkdump --hash`.

Evidence: [baseline equivalence](amd-2026-11-17/equivalence-baseline.log),
[paired equivalence](amd-2026-11-17/equivalence-paired.log),
[whole chunks](amd-2026-11-17/whole-chunks.log),
[validation commands/results](amd-2026-11-17/validation.txt).
External release-dump tests were skipped because their fixtures were unset.

## Scope and reproduction

Linux 7.2.14, Ryzen 9 7950X, RX 7900 XTX (`gfx1100`), HIP/ROCm
7.2.53211-3d9ef42, OCaml 5.4.0, Sarek `a16fa1f7` (library sources identical to
the project's pinned `d65ed53e`). The recorded GPU power cap was 291 W; it was
not changed. See [environment.json](amd-2026-11-17/environment.json).

Timing measures warmed, synchronous `Device_search.run_chunk` calls over whole
10^8-nonce chunks, including template updates, transfers and result handling.
The case-sensitive target `zzzzzzzzz` makes hits very rare. It excludes JIT and
initial context construction, and does not measure release-tool startup or
large-output workloads. Dumps are synthetic, 1024+F bytes, seed 20261117.
Results are local to this hardware/software/power configuration.

With the branch's dependencies installed in an OCaml 5.4 switch:

```sh
dune build
mkdir -p /tmp/hasher-amd
for f in 46 15 9 3; do
  dune exec test/support/mkdump.exe -- "$f" 20261117 "/tmp/hasher-amd/f$f.dump"
done
flock /tmp/katra-gpu.lock dune exec test/gpu_tune.exe -- \
  0 1.5 3 /tmp/hasher-amd/f46.dump /tmp/hasher-amd/f15.dump \
  /tmp/hasher-amd/f9.dump /tmp/hasher-amd/f3.dump
flock /tmp/katra-gpu.lock dune exec test/gpu_tune.exe -- \
  --variant 256:1 --variant 64:2 0 3 5 \
  /tmp/hasher-amd/f46.dump /tmp/hasher-amd/f15.dump
flock /tmp/katra-gpu.lock dune exec test/equivalence.exe -- --device 0 --interleave 2
for f in 46 15 9 3; do
  flock /tmp/katra-gpu.lock dune exec test/equivalence.exe -- \
    --device 0 --interleave 2 --whole-chunks 1 --dump "/tmp/hasher-amd/f$f.dump"
done
dune runtest
```

Check `--list-devices` before reusing device index 0 elsewhere. Keep the
paired variant opt-in for experiments; validate separately before selecting it
on another GPU or changing the production defaults.
