# Implementation Plan: GPU-Accelerated Tezos Protocol Vanity Hasher

**Branch**: `001-gpu-protocol-hasher` | **Date**: 2026-11-17 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-gpu-protocol-hasher/spec.md`

## Summary

`octez-vanity-gpu` is a drop-in replacement for the C vanity hasher used in Tezos protocol releases. Given the dump produced by `octez-protocol-compiler -dump-only` and a target name, it searches the 10^16 possible 16-digit nonces on a GPU. It prints `<protocol hash> <nonce>` for every match, in the C tool's format.

**Technical approach**, all validated by the prototype in `prototype/` (research R1–R4):
- The host computes the Blake2b-256 chaining value of the constant part of the dump once.
- Sarek kernels, generated fully unrolled, run one final-block compression per nonce. A few dump layouts need two compressions (case C in R2).
- The device filters candidates with integer intervals derived from the target, so it needs neither base58 nor SHA-256.
- The host confirms every hit with an independent reference.

The prototype measured 5.1·10^9 nonces/s on an RTX 5070 Ti, about 1,350 times the C hasher on 16 threads. It also reproduced the official hashes of the Seoul and Ushuaia protocols.

### Source Code (repository root)

```text
dune-project                      # package octez-vanity-gpu, generated .opam
gen/
└── gen_kernel.ml                 # writes the unrolled Sarek kernels, one per layout case (R2)
src/                              # library octez_vanity
├── blake2b.ml/.mli               # host Blake2b-256: compress, chaining value, full digest
├── dump.ml/.mli                  # load and validate the dump; layout case; chaining value; block templates
├── protocol_hash.ml/.mli         # prefix 0x02aa, double-SHA-256 checksum, base58check
├── target.ml/.mli                # name validation, case modes, exact rule, top64 intervals, expected rate
├── nonce_space.ml/.mli           # nonce ↔ digits, chunks, ranges, instance slices, seed → start
├── kernels.ml                    # generated by gen/ (dune rule): case A, B and C kernels
├── device_search.ml/.mli         # Sarek setup, per-case launch, hit buffer and overflow re-run (R9)
├── search.ml/.mli                # driver: range walk, host confirmation, stop conditions, signals, progress
├── verify.ml/.mli                # --verify: hash over the full dump (independent digestif path)
├── bench.ml/.mli                 # --bench: nonces/s per device and on the CPU backend
└── multi_device.ml/.mli          # one worker process per device, merged output (R7)
bin/
└── main.ml                       # cmdliner: search, --verify, --bench, --list-devices
test/
├── support/                      # fixtures.ml (external ground truth), mkdump.ml (synthetic dumps + digestif oracle)
├── unit/                         # alcotest + qcheck: blake2b vs digestif, base58, intervals, ranges, hit-buffer overflow
├── layouts/                      # synthetic dumps, final-block lengths 1–128, cases A/B/C
├── equivalence.ml                # device and Native vs the pure-OCaml reference; CUDA vs Native on whole chunks
├── vectors/c_hasher_pairs.txt    # (dump, nonce, hash) produced by the C hasher
└── cli/*.t                       # cram tests: output format, errors and exit codes, ranges and resume
prototype/                        # throughput prototype, kept as a reference; not part of the build
```

**Structure decision**:
- One dune project at the repository root: an internal library (`src/`), one executable (`bin/`) and a kernel generator (`gen/`) run by a dune rule.
- `prototype/` keeps its own `dune-project` and switch so that its measurements stay reproducible. The root project excludes it (`(dirs :standard \ prototype)`).
- The product is rebuilt cleanly from the prototype rather than grown out of it. `ref.ml` is split into `blake2b`, `dump`, `protocol_hash` and `target`, and kernel generation gains the B and C cases.

## Complexity Tracking

No constitution violations to justify. Two choices add complexity on purpose:

| Choice | Why needed | Simpler alternative rejected because |
|---|---|---|
| Three generated kernels (cases A/B/C) | Keeps one compression per nonce in about 96 % of layouts | One two-compression kernel: halves throughput for 85 % of dumps |
| One process per device | Sarek's device and kernel caches are not thread-safe | Domains in one process risk races; a single-thread round-robin serialises the GPUs |
